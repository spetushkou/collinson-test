# 2026-10-18 - setup, before the exercise starts

I did not start the exercise today. I spent the session preparing my tooling for it.

My agent harness came from a much larger product codebase, so most of it assumed things this
exercise does not have: a front end, a staging environment, a different ticket tracker, team chat.
I cut it down to what a small backend service needs and pointed the ticket workflow at GitHub
issues on this repo, with `status:` labels standing in for a status field.

Two calls shaped the rest:

- **The working trail lives here, in `docs/process/`.** The brief puts how I worked ahead of the
  service itself, and my harness is private, so anything worth seeing has to land in a tracked
  file.
- **AI use is stated here, not stamped on commits.** The brief asks me to use AI and show it. A
  plain description in this directory does that better than trailers on every commit.

Nothing about the service is decided yet - storage, the GraphQL library and the scoring model are
the first calls of the exercise, and they will go in `decisions.md` as I make them.

## Later: the scaffold

I picked NestJS, TypeScript and the Nest GraphQL adapter, and scaffolded a minimal service (issue
#1). Two things surprised me. The newest TypeScript and `graphql` are both ahead of what the Nest
and Apollo packages accept, so I pinned them back one major each. And I had planned on Jest
because I was told it was the Nest default - the generated project uses Vitest and oxlint, so I
kept those instead. Details in `decisions.md`.

## Later still: README, repo hygiene, hooks

- **README.** Written for the scaffold as it is - it says plainly that the ranking, the Open-Meteo
  client and storage are not built yet. I checked every command in it against a running service;
  my first draft promised the Apollo Sandbox at `/graphql`, but the service serves GraphiQL, so I
  fixed the text.
- **The brief stays out of the repo.** It is the hiring company's document, so it is gitignored
  and the README restates the task instead.
- **`CLAUDE.md` is public.** It is how I steer the agent, which is exactly the kind of "how you
  worked" the brief asks for. Anything private (my machine paths, harness wiring) stays in a
  separate, untracked file.
- **Server output goes to a log file.** Every `start*` script tees to `/tmp/collinson-api.log`, so
  a failed request can be read from the log instead of re-run. I wrapped it in
  `bash -c 'set -o pipefail ...'` - a plain `| tee` hides a crash behind `tee`'s exit code.
- **Supply chain: new package versions wait 7 days.** A scanner flagged the missing release-age
  setting. Adding it showed the lockfile already held versions only days old (Nest 12.1.3, Vitest
  4.1.12), so I rebuilt it and took the previous patch of each.
- **Wrong turn: `engine-strict`.** I turned it on to enforce the Node range, and it refused the
  install on my own machine - a package the Nest CLI pulls in wants a newer Node 22 patch than I
  have, though the service runs fine. Turned it back off and wrote down why in `.npmrc`.
- **Git hooks.** husky with commitlint (the `feature` commit type), lint-staged (prettier and
  oxlint on staged files) and a pre-push gate (lint, types, format, tests).
- **One ignore list, not three.** prettier and oxlint now take their ignore lists from
  `.gitignore` through a small generator with a drift check. oxlint needed it: it respects
  `.gitignore` when it walks a folder, but lints an ignored file when it is given the path
  directly - which is how the pre-commit hook calls it.
- **Formatting the docs exposed a bug in my own notes.** `decisions.md` used aligned
  "Options / Call / Why" lines, which Markdown renders as one run-on paragraph. They are bullets
  now.

## The exercise: design, plan, build

**Design first.** I talked the brief through with the model before any code: what the reviewer
should come away with (judgement on scope, not feature count), a one-day budget, SQLite through
Drizzle for storage, scores that explain themselves, and the cut list. Then I had it read the
Open-Meteo docs and probe the live API instead of trusting them. Three things came back that the
design leans on: the geocoder ranks by population, an unknown name is a 200 with no results (the
docs say 400), and the marine API answers an inland point with nulls rather than an error. A
fresh agent read the written design as a builder would and came back with six questions; I
settled them in the document. `design.md` and `plan.md` are the result.

**Wrong turn on the database driver.** I wanted Node's built-in SQLite so nothing would need a
native build. The docs showed a Drizzle driver for it, but it exists only in Drizzle's
prerelease. I switched to libsql, which ships prebuilt binaries, so the "nothing to install"
property survived.

**The build.** Nine issues under one epic, each through a branch and a pull request, merged in
order with CI green. Every PR got a code review by a separate agent before merging, and the
reviews were worth it - most found something real:

- eight parallel lookups of new cities gave one success and seven `SQLITE_BUSY` errors. A busy
  timeout does not fix it, because the driver is synchronous: the waiting connection blocks the
  one thread the transaction holding the lock needs to commit. Writes now go through one
  in-process queue;
- a calm, clear July day with no snow scored 10 for skiing, from wind and sky alone. The design
  said 0. I kept the design and added a "skiable snow" factor that cancels the rest;
- Open-Meteo picked its days with `timezone=auto` while the service used the geocoder's zone.
  Near a border they could disagree, the store would never hold the whole week, and every request
  would refetch. It now gets the place's own zone;
- one e2e test passed even with its failure switch removed. Now it fails without it - I checked;
- smaller ones: a base URL lost its path prefix, the database did not boot when started from
  another directory, a malformed 200 answer surfaced as a `TypeError`.

Not every finding held up: one claimed a bad config aborts with exit 134; it exits with 1, so I
left it and said so on the PR.

**Slips.** On #12 I wrote the service before running its tests, so I never saw them fail first.
The e2e tests that came after were written first. And while checking the README, Open-Meteo's
geocoding host stopped answering for a while - the service reported `UPSTREAM_UNAVAILABLE` as
designed, which was a better test than any I wrote.

**Later: an API page, and a bug it found.** I wanted a page of requests a reviewer can paste
(`docs/api.md`, #23), with every expected answer taken from a real run, not written from
memory. Running the examples taught me three things. Skiing scores 0 everywhere in October,
because snow depth is read at the town and not on the slopes - Zermatt, Tignes and Chamonix all
said so. So the page says that instead of hunting for a showcase. A postcode resolves (Q11). And
Longyearbyen broke the service: the geocoder sends no `country` for Svalbard, the column is
`NOT NULL`, and the answer was an `INTERNAL_SERVER_ERROR` with the SQL in it. That is #24, kept
out of the docs PR. A review of the page against the code found four statements I had wrong. The
one I would not have guessed: leave out `$city` and Apollo answers `BAD_USER_INPUT` with a 400,
so not every `BAD_USER_INPUT` is the service's own 200.
